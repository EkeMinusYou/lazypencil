# lazypencil フォントと対応環境

確認日: 2026-10-23

状態: macOS・Windows・Linux を対応目標とし、標準フォントに Noto Sans JP、端末画像に Kitty Graphics Protocol と Sixel を採用する。ユーザーによるフォント追加に対応する。具体的なフォントファイル・版と保証環境は初期検証で確定する。

## フォントの扱い

既存 `.pen` が指定するフォントを尊重し、新規文書には版を固定した標準フォントを使う。OS の標準フォントだけに依存せず、プロジェクトに必要なフォントを持ち運べる構成とする。指定と異なるフォントへの置換によって、既存文書の互換性を達成したとは扱わない。

### 標準フォント

新規文書の既定フォントには **Noto Sans JP** を採用する。日本語と英数字を一つのファミリーで扱い、基本パックを本体とともに提供する。Noto 全体を同梱する構成にはせず、明朝体・等幅書体・他言語・絵文字の追加フォントは用途に応じて導入できるようにする。[公式の収録文字の説明](https://raw.githubusercontent.com/google/fonts/main/ofl/notosansjp/DESCRIPTION.en_us.html)

ユーザーは OS へフォントをインストールするか、フォントファイルをユーザーの検索先またはプロジェクト内へ配置して設定から指定できる。プロジェクト内のファイルは OS へのインストールなしで利用できる。追加したフォントは CLI・MCP・TUI で共通して使い、AI による新規作成・編集でも指定できる。専用のフォント配信サービスや一覧カタログは必須にしない。

可変フォントの weight 軸を利用する案を第一候補にする。同じファイルで複数の太さを扱えるが、採用版の SkParagraph での選択・計測・描画を検証し、静的フォントの構成とも配布サイズとメモリを比較する。フォント名だけでなく、取得元のリビジョンとファイルの SHA-256 を固定する。[公式メタデータ](https://raw.githubusercontent.com/google/fonts/main/ofl/notosansjp/METADATA.pb)

Noto Sans JP の配布時は OFL 1.1 の著作権表記とライセンス本文を保持し、フォント自体のライセンスを表示する。本プロジェクトの MIT ライセンスに置き換えない。[付属ライセンス](https://github.com/google/fonts/blob/main/ofl/notosansjp/OFL.txt)

### 解決順と欠損

| 順序 | 解決先 | 扱い |
| --- | --- | --- |
| 1 | プロジェクト設定で指定したフォントファイル | プロジェクト相対パスを使い、OS へのインストールを不要にする |
| 2 | 同梱した標準パックの指定ファミリー | Noto Sans JP は同名のシステムフォントより固定版を優先する |
| 3 | ユーザー指定の検索先と OS のインストール済みフォント | ファミリー・スタイル・太さ・可変軸を照合し、実際のファイルを記録する |
| 4 | 明示したフォールバック列 | 指定フォントや文字が不足する場合に使い、標準パックも代替先にできる |

指定フォントが見つからない場合は、ノード・要求フォント・解決方法を診断する。TUI では代替プレビューを表示できるが、不完全な描画として表示する。CLI・MCP の通常の書き出しは既存の厳格な描画方針に従って失敗とし、明示的に部分描画を許可した場合だけ代替で出力する。代替のために `.pen` のフォント名を書き換えない。

フォールバック列は文字と言語に応じて解決し、日本語と他の CJK 言語の字形を区別する。文字や絵文字列を解決できない場合も診断する。絵文字はカラー形式・結合列・異体字セレクターを含めて検証し、OS ごとに異なる絵文字を無条件に再現可能とは扱わない。

フォントは明示的な導入操作で追加し、通常の描画でネットワークから自動取得しない。ユーザー所有のフォントをプロジェクトへ自動コピーする動作も設けず、利用者がファイルと配置先を指定する。

### 再現性と軽量性

プロジェクト設定でフォントファイル・フォールバック列・言語を指定する。再現用の補助ファイルには、ファミリー・スタイル・ファイルのハッシュ・可変軸・標準パックの版を記録する案を推奨する。補助ファイルで固定されているフォントと内容が異なる場合は診断し、厳格な出力では失敗にする。補助ファイルの具体的なスキーマは詳細設計で定める。

SkParagraph がファイルから読み込んだフォントで組版し、その結果を計測と描画の両方に使う。OS のフォント探索と、実際のフォント選択・文字計測を分ける。[Skia のフォント読み込み API](https://api.skia.org/classSkFontMgr.html)

フォントの全データ・全グリフを起動時に展開せず、使用するフェイスを遅延読み込みし、探索結果・組版・グリフのキャッシュに上限を設ける。任意の日本語を追記できるように、既存テキストの文字だけへ標準パックを削る構成は採らない。初回探索・初回読み込み・キャッシュ利用時を分けて計測する。

同じフォント・エンジン版・設定で、改行、文字位置、ベースラインと文書サイズを比較する。アンチエイリアスなどのピクセル差は別に評価し、同じフォントだけで全 OS の画像がバイト単位で一致するとは保証しない。

`browser` ノードはページ側の CSS と Web フォントを尊重する。通常の `.pen` の標準フォントを外部ページへ強制しない。固定ページによる比較試験では同じフォントを `@font-face` で供給し、フォントの準備を取得条件に含める。

TUI の会話・メニューの文字は端末のフォントに従う。デザインの文字は Skia で画像化するため、プレビュー用のフォントを端末へインストールする必要はない。

## クロスプラットフォーム

macOS・Windows・Linux で CLI・MCP・TUI と、JavaScript・Web ページ・シェーダーを含む共通機能の提供を目指す。Windows を初期リリースの対象外とする旧方針を変更する。

初期の検証・配布候補は次のとおりとする。これは動作確認済みの一覧ではない。

| OS | 初期の検証・配布候補 | 追加検証候補 |
| --- | --- | --- |
| macOS | Apple Silicon / Intel | 最低 OS バージョンを P0 で固定する |
| Windows | x86_64、MSVC | ARM64 のネイティブ実行 |
| Linux | x86_64、glibc 系 | ARM64、ディストリビューションの範囲 |

rust-skia は上記3 OS の x86_64・ARM64 向けプリビルドを提供している。ただし、それだけで lazypencil 全体の配布を保証するものではない。Linux のプリビルドには glibc・libstdc++ の条件があるため、本体と Chromium の両方を満たす対象ディストリビューション・版を固定する。[rust-skia の対応環境](https://github.com/rust-skia/rust-skia#platform-support-build-targets-and-prebuilt-binaries)

Chromium の配布物と必要なシステムライブラリ、JS エンジンのビルド、ソフトウェア WebGL、外部 AI アダプターを各対象で検証する。取得する実行環境は OS・CPU ごとに版とハッシュを固定し、配布元の対応表の存在だけで動作保証しない。[Chrome for Testing の提供状況](https://googlechromelabs.github.io/chrome-for-testing/)

OS 依存処理には、パス・設定保存先・ファイルロック・原子的な置換・子プロセス終了・端末制御を含める。Windows を WSL 上の Linux 動作だけで対応済みとは扱わない。OS ごとにネイティブ実行と保存・復旧を検証する。

### 端末内の画像

Kitty Graphics Protocol と Sixel の両方を初期リリースの対応対象とする。最初に Kitty を実装し、続いて Sixel を実装する。端末の応答で利用可否を調べ、設定でも選択できるようにする。Windows Terminal は Sixel に対応している。OS の対応と端末の画像プロトコルの対応は別々に公開する。[Microsoft の Sixel 対応紹介](https://devblogs.microsoft.com/commandline/windows-terminal-preview-1-22-release/)

Sixel では色の量子化、転送量、再描画・拡大縮小の応答も確認する。PNG 出力を画質の基準とし、端末内の表示方式による差を記録する。各 OS で少なくとも一つの端末による画像閲覧・日本語入力・キーボード操作を受け入れ条件にする。画像非対応端末では既存の外部ビューアへの導線を提供する。

P0 でクロスプラットフォーム上の問題が判明した場合は、機能または環境ごとに原因と対策を記録し、対応範囲の変更が必要なら判断材料を提示する。基本設計の時点で実機確認済みとは表現しない。
