# Design workflow

Start from the user's requested outcome, scope, and supplied material. Keep responses and design copy in the requested language. State assumptions only when they affect the result.

1. Open the intended .pen path with open_document, or use create_document for a new file. Pass the returned document_id to every document-specific MCP tool. IDs belong to one connection; reopen paths after reconnecting. Catalogue tools can query built-in resources without a document. Prefer absolute paths; relative paths use the server's working directory.
2. Read get_document and the relevant nodes. Use read_nodes directly for a known target, or search_nodes for shallow candidates and then read their returned read_target. Read only the descendant depth and collections needed for the task. The `operations` guide covers view selection, pagination, and edit requests.
3. Read the guides needed for the change and any trusted project_guides. Follow the user request, trusted project rules, selected style, then standard guidance. A project trust grant must come from the user. Preserve existing conventions when editing. For a new design, choose a supplied style only if it fits; an independent visual direction is also valid. Selecting a style does not modify the document.
4. For new or substantially changed compositions, establish the information hierarchy and the roles of color, spacing, and type. Use representative content and build the main regions before detail. Read `components` when elements should share future design changes; read `icons` before choosing icon names. A focused edit does not require redesigning the surrounding document or creating a design system.
5. Apply related edits in small atomic batches using current document and dependency revisions and returned IDs. Reconcile conflicts against the current document. Inspection requests need no edit batch. Use only advertised tools and supported capabilities.
6. Choose verification for the effect of the change. Queries about stored data and edits limited to organizational names or nonvisual metadata need no new layout or image unless requested. Structural changes need relevant reference checks. Changes to visible content, geometry, appearance, or dynamic behavior need calculated layout and image inspection; capture the initial design when its appearance is relevant to the edit. Follow `verification` for diagnostics, calculation reuse, and unavailable inputs. Report what changed or was inspected, the saved revision when applicable, and unresolved issues within the agreed scope and iteration limit.

## Select the relevant guides

Use `layout`, `typography`, and `color` for composition; `components` for shared definitions and instances; `effects` and `icons` for native graphics; and `operations` for API usage and a tested editing batch. `verification` explains checks and recovery. Read `app-screen`, `dashboard`, `content-page`, or `forms` for the corresponding content, rather than applying every pattern to every design. `scripts`, `browser`, and `shaders` cover optional dynamic content. Their linked specialist guides cover imports, browser configuration, and advanced shader inputs when needed.
