# Design workflow

Begin with the user's purpose, audience, content, target size, language, and reference images. State only assumptions that affect the result. Keep user-facing messages and design copy in the requested language; these English guides do not change that language.

1. When using MCP, open the intended absolute .pen path with open_document (or create_document for a new file) and pass its returned document_id to every document-specific tool. Document IDs, calculation IDs and cursors belong to one connection and document; reopen paths after reconnecting. Built-in guide/style catalogues and icons can be queried before opening. Read the document, local nodes, variable definitions, reusable components, and available fonts. get_document returns compact metadata by default; request include_capabilities:true for detailed feature support or include_configuration:true for full settings and origins. Query `list_icons` when adding icons and use advertised names and installed packs. Render an existing design before changing its visual conventions. Identify the region to change and the areas to preserve.
2. Read the relevant guides. Choose an available style for a new design when it fits the task. Read any trusted project_guides returned with this workflow, and follow the user request before project rules, selected style, and standard guidance. A project trust grant must come from the user; do not grant it yourself. For an existing design, prefer its own tokens, spacing, typography, and components. A style selection is a reference; it does not modify the document.
3. Define the information hierarchy and a small set of color, spacing, and type roles. Use real copy and representative data. Build the main regions first, then reusable elements and detail.
4. Apply small atomic batches using current document and dependency revisions. Use returned IDs; never invent a stored ID. Use client_ref and result_of when later operations in a batch need a newly created node. Review returned diagnostics: UNKNOWN_PROPERTY means a field was preserved but may have no effect. Correct spelling mistakes before claiming the requested change worked.
5. Inspect computed layout and current diagnostics using `validate_document` with `scope: "layout"`. Follow the user's requested scope, whether it is a node, a set of issues, or the whole document; a UI selection or attached reference does not override that scope. Read all diagnostic pages needed for that scope by passing `next_cursor` as `cursor` and reusing the returned `snapshot_id`. Inspect affected nodes before repairs; captured summaries may be stale. After repairs, validate the updated document with a fresh calculation, without the pre-edit snapshot ID or cursor, and check its relevant pages again. Render the whole target and inspect smaller regions when needed. Correct wrapping, alignment, spacing, contrast, and content problems. Keep refinement within the user's time and iteration limits.
6. Report the changes, preview, saved revision, and unresolved diagnostics. Distinguish a completed visual inspection from a render that was unavailable. Do not promise visual quality from structural validation alone.

Read `layout`, `typography`, `color`, `components`, `effects`, and `verification` as needed. `scripts` covers generated geometry and runtime dependencies; `browser` and `shaders` cover optional Chromium rendering. `operations` contains a tested editing batch. Task-specific advice is in `app-screen`, `dashboard`, and `content-page`. Query the current tool list and document capabilities before using a feature; do not invent a tool or claim an unsupported feature worked.

Calculation snapshots belong to the current MCP connection and can expire or be evicted. Do not assume that an ID in conversation history or a TUI preview is available for reuse. Before parallel calculated reads, obtain a retained snapshot from this connection and share its returned `snapshot_id`. On `SNAPSHOT_UNAVAILABLE`, request one fresh calculation without `snapshot_id` or `cursor`, then use its returned ID; do not repeat the missing ID or fan out fresh calculations. Keep edit batches sequential and use the revisions returned by the preceding batch.

Diagnostics are queryable document state, available through `validate_document` independently of TUI panes, prompt attachments, or the wording of a request. Its default `scope: "structure"` checks structure and references without executing scripts; `scope: "layout"` requires rendering support and adds measured layout diagnostics, including those shown in the TUI. For a document-wide inspection, read every page rather than inferring completeness from a visible list or summary count. See `verification` for scope, snapshot, and visual-check limitations.
